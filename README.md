## 1. 구현 내용

### 데이터: 과제 12, 13과 완전히 같은 데이터
- 과제 11~13과 같은 방법(`random_value()`: `rand()` 15비트 두 개를 이어 붙임)으로 0 ~ 2³⁰ − 1 범위의 무작위 정수를 만든다. 중복 값을 허용한다.
- n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 크기마다 원본 배열을 한 번만 만든다. 다섯 알고리즘은 모두 그 원본의 복사본(`memcpy`)을 정렬한다.
- `rand()`도 과제 12, 13과 같은 순서로 사용한다. 크기마다 데이터를 만든 직후 First → Random → Median3 순서로 정렬하는데, Random 피벗이 `rand()`를 쓰기 때문이다. 힙 정렬과 병합 정렬은 `rand()`를 쓰지 않으므로 순서에 영향이 없다.
- **확인**: 병합 정렬과 퀵 정렬 세 가지의 비교 횟수가 6개 크기 모두에서 과제 13(hw13_result.txt)과 정확히 같다. 예를 들어 n = 1,000에서 8,719 / 11,572 / 12,132 / 11,673이다. 즉 데이터가 같다.
- 모든 정렬 결과(측정 실행과 시간 실행 전부)가 오름차순인지 확인했다 → `Sort check : All results are sorted in ascending order`

### [1] 힙 정렬 (`heap_sort`, `sift_down`)
- 입력 배열 자체를 최대 힙으로 쓴다. 0번이 루트이고, i번의 자식은 2i+1, 2i+2다. 별도의 힙 배열은 만들지 않는다.
- 동작 순서
  1. **힙 구성**: 마지막 내부 노드(n/2−1)부터 루트까지 차례로 `sift_down`을 한다.
  2. **정렬**: 루트(최댓값)와 힙의 마지막 원소를 교환한다 → 힙 크기를 1 줄인다 → 루트에서 `sift_down`으로 힙 속성을 복구한다. 이것을 n−1번 반복한다.
- `sift_down`은 재귀 없이 반복문으로 구현했다. 내려가는 값을 따로 들고 있다가, 큰 자식을 한 칸씩 위로 올리고 마지막에 한 번만 쓴다.
- 비교 횟수: 한 단계 내려갈 때마다 최대 2회를 센다.
  - 두 자식 중 큰 쪽 고르기 1회 (오른쪽 자식이 있을 때만)
  - 내려가는 값과 큰 자식 비교 1회

### [2] 병합 정렬 (`merge_sort`, `merge_sort_rec`, `merge`)
- 과제 13과 같다. 하향식 재귀로, 반으로 나눠 각각 정렬한 뒤 병합한다.
- 크기 n인 임시 배열 하나를 정렬 시작 때 할당하고, 모든 병합에서 같이 쓴다.
- 비교 횟수: 병합할 때 두 부분의 맨 앞 값을 비교할 때마다 1회. 한쪽이 끝나면 남은 쪽은 비교 없이 복사한다.

### [3] 퀵 정렬 (`quick_sort`, `partition`, `select_pivot`)
- 과제 12, 13과 같은 구현이다. 세 방법은 피벗 선택(`select_pivot`)만 다르고, 분할(`partition`)은 같다.
  - **First**: 구간의 첫 번째 원소
  - **Random**: 분할할 때마다 무작위 위치를 새로 뽑음
  - **Median3**: 첫 번째, 가운데, 마지막 값 중 중앙값 (산술평균이 아님)
- 비교 횟수: 피벗과의 비교와 Median3의 중앙값 결정 비교(2~3회)를 센다. 인덱스·종료 조건 검사, 무작위 위치 생성, swap은 세지 않는다.

## 2. 측정 방법

알고리즘마다 **측정 실행 1회**와 **시간 실행 100회**를 따로 한다.

| 항목 | 방법 |
|---|---|
| 비교 횟수 | 측정 실행에서 데이터 값끼리 비교하기 직전에 카운터를 1 올린다. 인덱스·종료 조건 검사는 세지 않는다. |
| 실행시간 | 정렬 함수 호출 직전과 직후의 시각을 `QueryPerformanceCounter`로 잰다(Linux에서는 `clock_gettime(CLOCK_MONOTONIC)`). 크기마다 다섯 알고리즘을 **번갈아** 100회씩 정렬한 평균이고, 단위는 ms다. 데이터 생성, 배열 복사, 정렬 확인, 출력은 측정에서 빠진다. 다섯 알고리즘 모두 같은 방법이다. |
| 메모리 | 아래 3장의 방법으로 측정 실행 중 추적한 **최대 추가 메모리(Byte)** |

**측정 코드가 실행시간에 섞이지 않게 했다**
- 정렬 코드는 한 벌만 작성했다. 대신 `hw14.c`가 자기 자신을 두 번 `#include`해서 두 버전으로 컴파일된다.
  - 측정용 버전(`heap_sort_m` 등, `TRACK = 1`): 비교 횟수, 메모리, 재귀 깊이를 기록한다.
  - 시간용 버전(`heap_sort` 등, `TRACK = 0`): 측정 코드가 컴파일 단계에서 완전히 빠진다.
- 이렇게 한 이유: 측정 코드를 실행 중에 `if`로 끄기만 하는 방식으로 재 보니, 남아 있는 검사 비용이 알고리즘마다 달랐다. n = 20,000에서 힙 정렬은 27%, 퀵 정렬은 12%, 병합 정렬은 5% 느려졌다. 비교 검사가 가장 많은 힙 정렬이 가장 크게 손해를 봐서 공정한 비교가 아니었다.
- 다섯 알고리즘을 번갈아 실행하므로 CPU 클럭 변화나 캐시 상태 같은 측정 순서의 영향도 고르게 퍼진다.

## 3. 메모리 사용량의 측정 방법과 계산 기준

### 측정 방법: 실행 중 추적 (직접 계산)

- 정렬 함수들이 시작될 때 **자기 스택 프레임 크기만큼 현재 메모리에 더하고**, 끝날 때 뺀다.
- 동적 할당(병합 정렬의 임시 배열)도 할당할 때 더하고 해제할 때 뺀다.
- 정렬하는 동안 현재 메모리가 가장 컸던 값(peak)을 **최대 추가 메모리 사용량**으로 출력한다.

이렇게 하면 재귀가 가장 깊어진 순간에 동시에 쌓여 있는 프레임과 임시 배열의 합이 정확히 잡힌다. 고정된 공식이 아니라, 실제로 일어난 호출 순서와 재귀 깊이를 따라가며 계산한 값이다.

### 계산 기준

64비트 기준으로 int는 4B, 포인터는 8B로 계산했다. (Windows x64와 Linux x86-64가 같다)

**스택 프레임 1개 = 매개변수 + 지역 변수 + 호출 비용 16B**

- 호출 비용 16B는 복귀 주소 8B와 이전 프레임 포인터 8B다.
- 함수별 프레임 크기는 코드의 `FRAME_*` 매크로에 `sizeof`로 정의했다.

| 함수 | 매개변수 | 지역 변수 | 프레임 |
|---|---|---|---:|
| `heap_sort` | a(8), n(4) | i, tmp (8) | 36 |
| `sift_down` | a(8), root, size (8) | parent, child, tmp (12) | 44 |
| `merge_sort` | a(8), n(4) | temp 포인터(8) | 36 |
| `merge_sort_rec` | a, temp (16), left, right (8) | mid (4) | 44 |
| `merge` | a, temp (16), left, mid, right (12) | i, j, k (12) | 56 |
| `quick_sort` | a(8), n, method (8) | — | 32 |
| `quick_sort_rec` | a(8), low, high, method (12) | p (4) | 40 |
| `partition` | a(8), low, high, method (12) | p, pivot, i, j (16) | 52 |
| `select_pivot` | a(8), low, high, method (12) | — | 36 |
| `median_of_three` | a(8), low, high (8) | mid, x, y, z (16) | 48 |
| `swap` | a(8), i, j (8) | t (4) | 36 |

| 포함 | 제외 |
|---|---|
| 힙 정렬의 보조 변수와 호출 스택 | 원본 데이터 배열 (공통 비용) |
| 병합 정렬의 임시 배열과 재귀 호출 스택 | 표준 라이브러리 내부 (`rand`, `malloc` 관리 정보) |
| 퀵 정렬의 재귀 호출 스택과 보조 함수(피벗 선택, swap) 프레임 | 측정용 변수와 시간 측정 코드 |

※ 실제 기계어에서는 `/O2` 최적화 때문에 일부 변수가 레지스터에 올라가거나 함수가 인라인되어, 실제 스택 바이트는 이 값과 다를 수 있다. 위 기준은 **모든 매개변수와 지역 변수가 스택에 놓인다고 가정한 모델**이다. 세 알고리즘에 같은 규칙을 적용했으므로 서로 비교하기에는 공정하다.

## 5. 데이터 크기 증가에 따른 비교 횟수 변화

**n log n으로 증가한다**
- n이 2배가 될 때 비교 횟수는 다섯 방법 모두 2.04~2.33배로 늘었다. 16,000 → 20,000(1.25배)에서는 1.28~1.34배였다.
- n²에 비례한다면 4배, n에 비례한다면 정확히 2배여야 한다. 2배보다 조금 큰 것은 n log n에 비례한다는 뜻이다.

**비교 횟수 ÷ n log₂n**

| n | Heap | Merge | Quick (First) | Quick (Random) | Quick (Median3) |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 1.684 | 0.875 | 1.161 | 1.217 | 1.171 |
| 4,000 | 1.744 | 0.895 | 1.203 | 1.273 | 1.161 |
| 20,000 | 1.787 | 0.913 | 1.232 | 1.297 | 1.216 |

이 비율로 보면 순서가 모든 크기에서 **병합 (약 0.9) < 퀵 (약 1.2~1.3) < 힙 (약 1.7~1.8)** 으로 같다. 힙 정렬은 병합 정렬의 약 1.93~1.96배, 퀵 정렬의 약 1.4~1.5배를 비교했다. 이 차이는 각 알고리즘의 동작 방식에서 나온다.

- **병합 정렬 (약 0.9 n log₂n)**
  - 이미 정렬된 두 부분을 합치므로, 비교 한 번마다 원소 하나의 최종 위치가 정해진다. 비교를 낭비하지 않는다.
  - 한쪽이 먼저 끝나면 남은 쪽은 비교 없이 복사한다. 그래서 병합 한 번의 비교는 두 부분 길이의 합보다 적다.
  - 이론값 n log₂n − 1.25n과 거의 같다. (n = 1,000: 이론 8,716 / 측정 8,719, n = 20,000: 이론 260,754 / 측정 260,943)
- **퀵 정렬 (약 1.2~1.3 n log₂n)**
  - 한 번 분할할 때 구간 전체를 피벗과 비교한다.
  - 피벗이 정확히 중앙값이 아니어서 분할이 고르지 않다. 그만큼 재귀 트리가 log₂n보다 깊어지고 비교 횟수가 늘어난다.
- **힙 정렬 (약 1.7~1.8 n log₂n)**
  - 원소 하나를 꺼낼 때마다 루트에서 바닥까지 약 log₂n 단계를 내려간다.
  - 단계마다 비교가 **2회** 필요하다. 두 자식 중 큰 쪽 고르기 1회, 내려가는 값과 비교 1회다.
  - 게다가 루트로 올라온 값은 원래 힙의 맨 끝(작은 값)이었기 때문에, 거의 항상 바닥까지 다시 내려간다.
  - 그래서 이론값 약 2n log₂n에 가까워진다. n이 커질수록 비율이 1.68 → 1.79로 2에 다가간다.

## 6. 실행시간 차이

**힙 정렬 < 퀵 정렬 < 병합 정렬 순으로 빨랐다**
- 힙 정렬이 모든 크기에서 가장 빨랐다. 퀵 정렬(First)보다 1.7~2.0배, 병합 정렬보다 1.9~2.5배 빠르다.
- 병합 정렬은 n ≥ 2,000에서 가장 느렸다. 퀵 정렬(First)보다 1.13~1.27배 느리다.
- 힙 정렬의 실행시간은 n이 2배가 될 때 1.97~2.10배씩 늘었다. 비교 횟수처럼 n log n으로 늘어난다.

**비교 횟수 순서와 실행시간 순서가 정반대다**
- 비교가 가장 많은 힙 정렬이 가장 빠르고, 비교가 가장 적은 병합 정렬이 가장 느렸다.
- 비교 1회당 시간을 보면 이유를 알 수 있다.

| | Heap | Merge | Quick (First) | Quick (Random) | Quick (Median3) |
|---|---:|---:|---:|---:|---:|
| 비교 1회당 시간 (ns, n = 20,000) | **1.41** | 5.88 | 3.55 | 3.73 | 3.77 |

실행시간은 비교 횟수만으로 정해지지 않는다. 비교 외에 하는 일(데이터 이동, 함수 호출, 메모리 접근)이 함께 결정한다.

- **힙 정렬: 비교 1회당 시간이 가장 짧다.**
  - `heap_sort`와 `sift_down`은 재귀가 없다. 반복문 안에서 인덱스 계산(2i+1)과 비교만 한다. 함수 호출은 `sift_down` 약 1.5n번(힙 구성 n/2 + 정렬 n−1)뿐이다.
  - `sift_down`은 값을 매번 교환하지 않는다. 큰 자식을 한 칸씩 올리고 마지막에 한 번만 쓰므로, 한 단계에 쓰기가 1회다.
  - 그래서 비교는 가장 많지만 비교 사이에 하는 일이 거의 없어 전체 시간이 가장 짧았다.
  - 단, n = 20,000이어도 배열이 80KB라 CPU 캐시에 다 들어간다. 그래서 힙 정렬의 약점인 **멀리 떨어진 위치(i와 2i+1)를 오가는 메모리 접근**이 드러나지 않았다. 데이터가 캐시보다 훨씬 커지면 힙 정렬은 캐시 미스 때문에 느려지는 것이 일반적이다.
- **병합 정렬: 비교 1회당 시간이 가장 길다.**
  - 병합할 때마다 구간 전체를 임시 배열로 옮겼다가 원래 배열로 되돌린다. 같은 데이터로 잰 과제 13의 기록에서 n = 20,000일 때 데이터 이동이 574,464회로, 퀵 정렬(약 16만 회)의 3.5배였다.
  - 원소 하나짜리 구간까지 재귀하므로 재귀 호출이 2n − 1번(n = 20,000이면 39,999번) 일어나고, 병합 함수 호출도 n − 1번 더 있다.
  - 비교는 가장 적지만 복사와 호출 비용 때문에 가장 느렸다.
- **퀵 정렬: 중간**
  - 제자리에서 양 끝부터 차례로 읽고 필요할 때만 교환하므로, 병합 정렬보다 이동이 훨씬 적고 메모리를 차례대로 접근한다. 그래서 병합 정렬보다 빨랐다.
  - 하지만 분할마다 `partition`, `select_pivot`, `swap` 등 함수 호출이 있고, 재귀 호출도 n번 이상 일어난다. 그래서 반복문만 도는 힙 정렬보다 비교 1회당 비용이 2.5배쯤 크다.
- **Quick (Random)이 퀵 정렬 중 가장 느렸다.**
  - 모든 크기에서 First보다 약 10~15% 느렸다.
  - 비교 횟수는 First와 비슷하다(최대 6% 많음). 대신 분할할 때마다 `rand()`를 호출한다. `rand()`는 비교보다 훨씬 비싼 라이브러리 함수라서 그 시간이 더해졌다.

## 7. 메모리 사용량 차이

**힙 정렬: 80B로 크기와 관계없이 일정 → O(1)**
- 입력 배열 안에서 힙을 만들고 정렬한다.
- `sift_down`이 재귀 없이 반복문이라, 동시에 존재하는 프레임은 `heap_sort`와 `sift_down` 두 개뿐이다 (36 + 44 = 80B).

**병합 정렬: n에 비례해 증가 → O(n)**
- n이 2배가 되면 메모리도 거의 정확히 2배가 된다 (4,532 → 8,576 → 16,620 → …).
- 대부분은 임시 배열 4n Byte다 (n = 20,000에서 80,000B).
- 재귀 스택은 깊이 ⌈log₂n⌉ + 1 = 11~16 단계라서 수백 B밖에 안 된다.
  - 예: n = 1,000일 때 36(`merge_sort`) + 4,000(임시 배열) + 10 × 44(재귀) + 56(`merge`) = **4,532B**. 측정값과 정확히 같다.
- 다섯 방법 중 가장 많다. n = 20,000에서 힙 정렬의 약 1,000배, 퀵 정렬의 약 56~59배다.

**퀵 정렬: 재귀 깊이에 비례 → 평균 O(log n)**
- 추가 배열 없이 재귀 호출 스택만 쓴다.
- 그래서 메모리는 (최대 재귀 깊이) × 40B + 분할·피벗 선택 프레임으로 정해진다.
  - 예: Median3, n = 1,000일 때 분할이 깊이 15에서 일어났다. 32 + 15 × 40 + 52(`partition`) + 36(`select_pivot`) + 48(`median_of_three`) = **768B**.
- n이 20배 커지는 동안 메모리는 약 1.5~1.8배만 늘었다. 깊이가 log n으로 천천히 늘기 때문이다.
- **피벗에 따라 메모리가 달라진다.**
  - Median3는 분할이 고르기 때문에 n = 16,000까지 깊이가 16~25로 가장 얕고, 메모리도 768~1,128B로 가장 적었다.
  - First와 Random은 깊이 21~34, 메모리 920~1,440B다.
  - 단, n = 20,000에서는 Median3의 깊이가 31로 First(32)와 거의 같아져 메모리가 1,368B로 First(1,360B)보다 8B 많았다. 재귀 깊이는 가장 불운했던 한 경로가 정하므로, 평균적으로 고른 분할을 하는 Median3도 한두 번 나쁜 분할이 겹치면 깊어질 수 있다.

## 8. 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

| | First | Random | Median3 |
|---|---|---|---|
| 비교 횟수 (6개 크기 합계) | 846,809 | 871,807 | **828,091** |
| 실행시간 | **가장 빠름** | 항상 가장 느림 (First보다 10~15%↑) | First와 비슷 (0.8~8%↑) |
| 최대 재귀 깊이 / 메모리 | 21~32 / 920~1,360B | 22~34 / 960~1,440B | **16~31 / 768~1,368B** |

- **Median3가 비교 횟수와 메모리에서 가장 좋았다.**
  - 세 값의 중앙값은 원소 하나를 뽑을 때보다 실제 중앙값에 가까울 확률이 높다. 그래서 분할이 고르게 된다.
  - 분할이 고르면 재귀 트리가 얕아진다. 그러면 비교 횟수(깊이 × n)와 스택 메모리(깊이 × 프레임)가 함께 줄어든다.
  - 비교 횟수는 6개 크기 중 5개(2,000 이상)에서 가장 적었다. 중앙값을 정하느라 분할마다 2~3회를 더 비교하지만, 고른 분할로 아끼는 비교가 더 많다.
- **실행시간은 First가 가장 빨랐고 Median3와 차이가 작았다.**
  - Median3는 비교가 First보다 1~4% 적다(n ≥ 2,000). 하지만 분할마다 `median_of_three` 호출과 세 원소 읽기가 더해진다. 그래서 시간 이득이 상쇄되어 First와 비슷하거나 조금 느렸다. (n = 1,000에서는 3번 중 2번 Median3가 더 빨랐다.)
- **First와 Random은 비교 횟수가 비슷했다.**
  - 데이터가 무작위라서 첫 번째 원소도 사실상 무작위 원소와 같다. 그래서 두 방법의 분할 결과 분포가 같다.
  - 실행시간은 Random이 `rand()` 호출 비용만큼 항상 느렸다.
- **First의 위험**
  - 정렬된 데이터나 역순 데이터를 넣으면 First는 매번 최솟값이나 최댓값을 피벗으로 고른다.
  - 그러면 비교 O(n²), 재귀 깊이 n이 된다. 메모리도 O(n)이 되어 n = 20,000이면 약 800KB이고, 스택 오버플로가 날 수 있다.
  - 이번 무작위 데이터에서는 이 약점이 드러나지 않았다. 실제로 쓰기에는 Median3가 가장 안전하다.

## 9. 시간 복잡도 및 공간 복잡도 비교

| 알고리즘 | 최선 | 평균 | 최악 | 추가 공간 | 이번 실험에서 확인한 것 |
|---|---|---|---|---|---|
| 힙 정렬 | O(n log n) | O(n log n) | O(n log n) | **O(1)** | 비교 ≈ 1.7~1.8 n log₂n (가장 많음), 시간은 가장 짧음, 메모리 80B로 일정 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n log n) | O(n) | 비교 ≈ 0.9 n log₂n (가장 적음), 시간은 가장 김, 메모리 ≈ 4n B |
| 퀵 정렬 | O(n log n) | O(n log n) | **O(n²)** | 평균 O(log n), 최악 O(n) | 비교 ≈ 1.2~1.3 n log₂n, 시간은 중간, 메모리는 재귀 깊이에 비례 (약 0.8~1.4KB) |

**힙 정렬**
- 입력 순서와 관계없이 항상 n log n이 보장된다.
- 추가 메모리도 거의 없다.
- 비교가 가장 많지만, 반복문만 쓰는 단순한 구조라 이번 실험(데이터가 캐시에 들어가는 크기)에서는 가장 빨랐다.
- 대신 멀리 떨어진 위치를 오가며 접근해서, 캐시보다 큰 데이터에서는 불리하다. 안정 정렬도 아니다.

**병합 정렬**
- 항상 n log n이고 비교도 가장 적다. 같은 값의 순서가 유지되는 안정 정렬이다.
- 대신 n 크기의 임시 배열과 데이터 복사 비용이 들어 메모리와 실행시간이 가장 컸다.

**퀵 정렬**
- 이동이 적고 메모리 접근이 차례대로라서 병합 정렬보다 빠르다.
- 추가 메모리도 log n 수준이다.
- 대신 피벗이 나쁘면 O(n²)이 된다. 그래서 Median3 같은 피벗 선택이 중요하다.

## 10. 결론

| 기준 | 가장 좋았던 알고리즘 | 이유 |
|---|---|---|
| 비교 횟수 | 병합 정렬 | 정렬된 두 부분을 합치는 방식이라 비교 1회마다 원소 하나가 확정됨 |
| 실행시간 | 힙 정렬 | 재귀·함수 호출 없이 반복문만 돌고 이동이 적어 비교 1회당 비용이 가장 작음 (데이터가 캐시에 들어가는 크기에서) |
| 메모리 | 힙 정렬 | 입력 배열 안에서 정렬하고 재귀가 없음 (O(1)) |
| 퀵 정렬 피벗 | Median-of-Three | 분할이 고르게 되어 비교 횟수와 재귀 깊이, 메모리가 대체로 가장 적음 |

비교 횟수가 가장 적은 병합 정렬이 가장 느렸고, 비교가 가장 많은 힙 정렬이 가장 빨랐다. 정렬 알고리즘의 실제 성능은 비교 횟수뿐 아니라 데이터 이동량, 함수 호출, 메모리 접근 방식에 함께 좌우된다는 것을 실험으로 확인했다.

※ 실행시간은 CPU, 컴파일러, 최적화 옵션, 시스템 부하에 따라 달라진다. 위 실행시간 표는 Windows 64비트, MSVC `/O2` 환경에서 측정한 값이다.
